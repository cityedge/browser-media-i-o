# 次期実装計画：連続読み取りとWorker対応のメディア入出力

作成日: 2026-10-03（日本時間）
更新: 動画編集アプリ側の計画レビューを反映（2026-10-03、日本時間）。

0.2の承認済み計画に沿って実装・検証を完了しました。現在の契約は [API](API.md)、
測定結果・制限・再現手順は [0.2評価結果](VALIDATION_0.2.md) を参照してください。
以下は承認時の設計と後続の0.3計画です。「現行コードと依存実装で確認したこと」は
計画時のコミット `885edd1` とMediabunny 1.61.0についての調査記録です。

0.2の実装では公開API名を計画どおり採用しました。キャンセル完了を保証するため、固定依存の
内部hook二つを `src/decoder-session.ts` に隔離して使用しています。基盤のreturnをそのまま返す方式ではありません。
videoFramesAtは基盤のsamplesAtTimestampsを直接使わず、逐次sampleと最大2枚の保持で時刻列を処理します。
0.3のレート変換、パケット時刻API、編集・合成機能は今回の実装に含みません。

0.2.1では、この終了保証を持つ従来APIを残し、公開APIだけを使う `browser-media-io/public` を追加しました。
公開API版のreturn完了点はラッパーの待機終了・結果破棄・入力排他解除です。基盤の背景処理の終了待ちは含めません。
以下の強い終了保証は従来APIに対する計画として保持します。比較は [API契約](API.md#入力apiの選択021) を参照してください。

ライブラリは「必要な時刻のメディアを、時刻情報を保って読み、完成した映像・音声を書き出す」部分を担当します。
編集の意味、描画、音声ミックス、再生スケジュールはアプリが担当します。

全曲分の動画を同時にデコードする構成を前提にしない。合成式や曲の配置は評価アプリが担当する。

## 現行コードと依存実装で確認したこと

- `src/input.ts`: `#busy` はMediaInput全体を排他制御する。`audioBlocks()` の反復中も他操作はBUSY。
  `openMedia` のsignalは入力全体を閉じる。個々の読み取りへのsignalはない。
- 同じBlobを複数の `openMedia` で開くことは現行APIでも可能で、別入力の並行利用はすでに文書化されている。
  次版では同一素材の映像／音声／プレビューを分ける使い方を、サンプルと回帰テストで保証する。
- Mediabunnyの `VideoSampleSink.samples()` は表示順の連続取得を提供する。
  `samplesAtTimestamps()` は時刻列による取得を提供し、単調な時刻列ではデコードを再利用する。
  現行の単発 `getSample()` 呼び出しだけでは、この時刻列向けの最適化を利用できていない。
- 同基盤のイテレーターには `return()` と内部キューの制御がある。一方、公開APIには任意の先読み枚数を
  指定する設定がなく、`return()` の完了と内部デコーダー処理の完全な終了が同時とは限らない。
  単にPromiseの待機を中止するだけでは、読み取りキャンセルの実装として不十分。
- `AudioSampleSink` と生PCMからの `AudioSample` 構築があり、Web Audioを使わない経路を作る足場がある。
  現行writerも内部ではPCM配列を `AudioSample` に渡しているが、入口はAudioBufferに限定している。
- 内蔵の音声変換にはレート変換があるが、1.61.0では線形補間で、ダウンサンプリング用の低域通過フィルターがない。
  また、同じ音声sourceに途中から異なる入力サンプルレートを渡すと拒否する。
- `EncodedPacketSink.packets({metadataOnly:true})` 相当の経路は既存probeで使用中。
  正確な呼び出しは `packets(undefined, undefined, {metadataOnly:true})`。
  返却順はデコード順で、表示時刻順ではない。sequenceNumberも表示フレーム番号ではない。
- トラックの `getTimeResolution()` と `getColorSpace()`、デコードsampleの色空間は基盤にある。
  現行ラッパーはそれらを公開していない。
- 基盤の `VideoSample` はrotation、flip、回転前の表示寸法を持つ。回転は時計回りで、水平反転は回転後。
  `draw()` はこれを適用するが、`toVideoFrame()` はその表示変換を画素に焼き込むAPIではない。
  現行MediaFrameはrotationだけを公開しており、WebGLで表示を再現するには情報の補完が必要。
- ストリーム出力でも通常MP4の索引は尺に応じて増える。現行仕様もメモリ完全一定を保証していない。

## 0.2：連続読み取りとPCM入出力

### 1. 読み取りを個別に中止できるようにする

既存の入力全体を閉じるsignalは残し、各読み取りにも独立したsignalを追加する。
映像・音声の新しいイテレーターに加え、単発フレーム取得、既存audioBlocks、probeも共通の制御に揃える。

- 個別abortは該当読み取りだけを中止する。入力は再利用できる。
- `break`、例外、`iterator.return()`、入力closeでも、内部イテレーターと未返却sampleを片付ける。
- `next()` が待機中の場合も中止でき、遅れて届いたsampleは返さず解放する。
- 読み取り中止後にBUSYが残らず、同じ入力でシークを再開できるようにする。
- 返却済みMediaFrameは利用側が所有し、個別abortでは勝手に閉じない。
  既存契約に合わせ、入力全体のcloseはその入力の未解放ハンドルも閉じる。
- ブラウザー内部の処理終了まで含めた、全環境共通の固定キャンセル時間は保証しない。

**再利用可能になる完了点は、ラッパーの `await iterator.return()` の成功時とする。**
`AbortController.abort()` は中止要求であり、その呼び出しから戻っただけでは再開可能とはみなさない。
待機中の `next()` がABORTEDで終了した場合も、確実な再開にはreturnを待つ。

```ts
// 計画上の待ち方。進行中のnext()の結果・例外も、呼び出し側の読み取りループで処理する。
readController.abort();
await reader.return();
// 入力自体がcloseされていなければ、ここから同じmediaで次の読み取りを開始できる。
const nextReader = media.videoFramesAt(nextTimes, { signal: nextController.signal });
```

- returnは反復呼び出し可能とし、既に中止・自然終了したreaderにも安全に使える。
  待機中のnextがあっても終了処理を進め、return成功までにその待機を解決またはrejectする。
- return成功時には該当readerの排他状態を解除する。旧結果は新readerに渡さず、返却前の結果は解放する。
  abortと競合して既に利用側へ渡ったフレームには、返却済みフレームの所有権規則を適用する。
  利用側が所有するフレームのclose待ちはreturn完了の条件に含めず、未解放ハンドル数の上限は再開後も維持する。
- 自然終了の `{done:true}` も同じ終了処理を通す。`for await` のbreakは暗黙のreturnが完了してから抜ける。
  単発取得やprobeは、個別キャンセルによるPromiseの終了を、その操作の再利用可能な完了点とする。
- 終了処理が失敗した場合は成功として通知せず、入力を再利用できるとは報告しない。
  入力全体のclose後は、readerの終了を待っても入力自体は再利用できない。

内部では読み取りごとに結果を識別し、中止された処理から遅れて届く結果を破棄・解放する。
資源の停止・解放を確認する前に、BUSYだけを解除して次のデコーダーを次々に起動する方式にはしない。
ブラウザー側の実メモリ回収が遅れても、ライブラリの未完了処理・旧デコーダー・キューが反復回数に比例して
積み上がらないことを計測する。解放可能になったメモリのGC時刻までは完了点の保証に含めない。

基盤のreturnをそのまま返して、この契約を満たしたと扱わない。実装の最初に初期化中・next待機中・
yield中の停止を検証する。固定版の公開APIだけで必要な終了管理が成立しない場合は、
依存の修正／更新や読み取り管理の設計変更を別途検証し、契約を満たしてから0.2をリリースする。

まず0.2は同一MediaInputの排他制御を維持する。映像と音声を同時に読む場合は同じBlobを別々に開く。
これにより、プレビューの中止と書き出しの中止も独立させられる。ファイルをJSで丸ごと複製する必要はないが、
キャッシュ・解析情報・デコーダーのメモリは入力数に応じて増える。
同一入力に複数readerを作ってキャッシュを共有するAPIは、実測で必要性が出た場合の後続改善とする。

### 2. 二つの映像取得方法を追加する

```ts
media.videoFrames({ start, end, trackId, signal });
media.videoFramesAt(times, { trackId, signal });
```

`videoFrames` は元の映像フレームを表示時刻順に返す。指定範囲は `[start,end)` とし、その範囲と
表示区間が重なるフレームを対象にする。startより前に始まっていてもstartで表示中のフレームは含める。
元のtimestamp／durationを保持し、勝手に出力用fpsへ変換しない。

フレームの表示区間も `[timestamp, timestamp + duration)` とする。
videoFramesの採用条件は、この区間と要求区間の重なりがあること、すなわち
`timestamp < end && timestamp + duration > start`。durationが0なら空区間として返さない。
開始時刻で表示中のフレームは含むが、startちょうどで終わるフレームやendちょうどから始まるフレームは含めない。

`videoFramesAt` はアプリが指定する単調非減少の時刻列を受け取り、各時刻で表示されるフレームを返す。
同時刻の繰り返しを許し、逆向きシークは現在の読み取りを終了して新しい列で開始する。
素材のない時刻はnullとし、同じ元フレームが複数回選ばれた場合も、個別にcloseできる所有権を確保する。
有効な要求時刻tに対し、`timestamp <= t && t < timestamp + duration` を満たすフレームだけを返す。
先頭より前、末尾の終了時刻ちょうどとそれ以降、途中の表示区間の空白ではnullを返す。
終了時刻ちょうどに次のフレームが始まる場合は次のフレームを返し、終了したフレームは返さない。
基盤の「t以前に始まった最後のフレーム」をそのまま採用せず、この表示区間判定をラッパーで行う。
`getVideoFrame()` とも判定を共通化する。
返却値には要求時刻と、取得したフレームの元時刻を区別して持たせる。
時刻列は逐次消費し、全件を配列に展開しない。0.2では同期の `Iterable<number>` を対象とし、
外部の非同期処理が時刻を供給するAPIは後続の必要性を見て判断する。

この入口があると、29.97fps／30fps／可変fpsの素材でも、アプリが同じ出力時刻列を渡して合成できる。
出力時刻を作ること、素材上の時刻への変換、欠落時に前フレームを保持するか等はアプリが決める。

利用側は返されたフレームを `try/finally` でcloseする。ライブラリ独自の先読みキューは初期実装では増設せず、
基盤の逐次取得と処理待ちを利用する。既存 `maxOutstandingFrames` は利用側へ返したハンドルの上限として維持する。
上限違反は明示的なエラーにし、解放し忘れたフレームを無期限に待つ方式にはしない。
基盤キュー・デコーダー参照画像まで含めた厳密なメモリ上限とは区別する。

時刻比較はWebCodecsのµs精度を踏まえた共通の正規化規則を仕様化し、秒の浮動小数点加算だけに依存しない。
丸めの規則は要求時刻とフレーム境界に一貫して適用し、広いepsilonで終了後や空白区間を埋めない。
正規化された境界の直前・一致・直後を明示的にテストする。

0.2の境界・所有権の回帰テストは次を必須とする。

| ケース | 期待結果 |
|---|---|
| startがフレーム表示区間の途中 | videoFramesは表示中の最初のフレームを含む |
| フレームがstartで終了／endで開始 | videoFramesはそのフレームを返さない |
| 開始オフセットのある素材で先頭より前を要求 | videoFramesAtはnull |
| 末尾の終了時刻ちょうど／それ以降を要求 | videoFramesAtはnull |
| 途中に実際の表示空白がある素材 | 空白ではvideoFramesAtはnull。videoFramesは空白だけの範囲にフレームを返さない |
| 前フレームの終了と次フレームの開始が一致 | 一致時刻では次フレーム。終了した前フレームは返さない |
| 同じ時刻の反復／同じ元フレーム内の異なる時刻 | 返却物は独立し、一方をcloseしても他方をdraw／toVideoFrameで使用できる |

空白・オフセットは素材の実タイムスタンプとして用意し、アプリ側で黒を描いた区間で代用しない。
有限・非負などの引数検証と、有効な要求時刻に対するnullの判定は区別する。

### 3. Workerで使うPCM経路を追加する

```ts
media.audioPcmBlocks({ start, end, trackId, signal });
writer.addPcm(pcm);
```

PCMの基本形は、サンプルレート、チャンネル数、チャンネル当たりのサンプル数、
チャンネル別の `Float32Array` とする。入力ブロックには元素材のtimestampを付ける。
最大ブロック長を制限し、切り出しは現在と同じくサンプル境界で行う。

- 入力PCMは利用側所有のJS配列。次の読み取りで内容を書き換えない。closeは不要で、参照を手放せば解放対象になる。
- Worker間のtransferが可能な通常のArrayBufferを使う。基盤のデコードsampleはコピー後すぐcloseする。
- writerはPCMを借用し、勝手にdetachしない。利用側はaddPcmの完了まで書き換え・transferしない。
  内部の必要なコピー量と、完了後に再利用できることを文書化する。
- writerへの追加は従来どおり0秒から連続。元素材のtimestampによる配置・無音埋めはアプリ側。
  出力時刻は累積整数サンプル数から計算する。
- 0.2では出力設定と異なるレート・チャンネル数を拒否する。自動変換を隠れて行わない。
- 既存 `audioBlocks()`／`addAudio(AudioBuffer)` は互換用として残し、PCM経路を共通の内部処理にする。
  `decodeAudio()` は従来のWindow向け全デコード補助APIとして残す。
- AudioDataの直接受け渡しは、コピー削減の効果を測ってから追加判断する。0.2の必須APIにはしない。

ライブラリはDedicated Worker内でのprobe、区間デコード、OffscreenCanvas／VideoFrame入力、
PCM入力、MP4確定までを検証する。AAC拡張は実行するWorker側で明示的に登録し、
拡張が内部生成するWorkerの初期化・中止も確認する。
Workerの起動、UIとの通信、ファイル選択、保存ハンドルの受け渡しはアプリの責任とし、サンプルで示す。

### 4. WebGL経由の入出力と表示変換を検証する

完成したプレイヤーやマット合成機能を作らず、次の経路を示す最小サンプルを用意する。

```text
動画取得 → toVideoFrame() → WebGLのテクスチャ描画
        → Canvas／OffscreenCanvas、または描画結果のVideoFrame → addVideoFrame() → MP4
```

独立した二動画を同じ出力時刻で読み、単純な並列配置などで両方の内容を確認する。
非対称な四隅の目印と、黒・白・段階的なグレーを使い、向き・範囲・画素値を比較する。
Canvasを直接writerへ渡す場合と、描画結果をVideoFrameにして渡す場合を両方テストする。
Worker＋OffscreenCanvasの経路も0.2の必須検証に含める。

- `MediaFrame.flip` を追加し、回転後の画像を水平反転する真偽値として定義する。
  GPU側が表示サイズを再現するために必要な回転前の表示寸法も公開する（squarePixelWidth／squarePixelHeightを候補）。
  現行width／heightが回転後の表示寸法である意味は維持する。
- `draw()` は表示変換を適用済み。`toVideoFrame()` はその変換を画素へ焼き込まず、
  GPU経路では回転前の表示寸法を基準に、時計回りのrotation、続いて水平flipを利用側で適用する。
  VideoFrameのvisibleRectと表示寸法の扱いもサンプルに記載する。
- サンプルの画素アスペクト比調整と0／90／180／270度回転、flip有無の組み合わせで、
  drawとWebGL経路が同じ表示範囲・向きになることを比較する。
  任意のアフィン変換、せん断、特殊なコンテナ行列の完全再現は0.2の対象に含めず、対応範囲を文書化する。
- WebGLのテクスチャ座標の上下反転と、素材の水平flipを混同しない。
  色変換・アルファ・描画バッファ保持等のコンテキスト設定とアップロード設定をサンプルで明示する。
  描画後のどの時点でCanvasを渡す／VideoFrameへスナップショットするかも示し、awaitをまたいだ空の出力を防ぐ。
- 元MediaFrame、toVideoFrameで作る別所有のフレーム、出力用フレーム、GPU資源はそれぞれ解放する。
  addVideoFrameは利用側のVideoFrameを勝手にcloseしない現行契約を維持する。

向きと範囲は既知の目印で判定し、画素値はWebGL描画直後とMP4再デコード後で分けて検査する。
Canvas 2D経路との比較に加え、元の既知のパターンも正解として使う。
色差の許容値は入力経路・コーデック・環境とともに記録する。非可逆圧縮後の完全一致は要求しない。
グレーマットの合成式・補正方法はアプリ側の責務を維持する。

### 0.2の完成条件

1. Bフレーム・可変fps・開始オフセットを含む入力で、連続取得と指定時刻取得が独立したFFmpegの正解と一致する。
2. 同一ファイルの映像／音声を別入力で処理し、片方を中止してももう片方が正常に進む。
3. 初期化中・next待機中・yield中の中止でreturn完了を待ち、直後に同じ入力を再利用できる。
   二動画の取得・逆向きシーク・中止を反復しても、旧結果が混入せず、旧デコーダーやキューが累積しない。
4. 遅い消費側でライブラリ独自の待ち行列が増え続けない。返却済みフレーム、キャッシュ、基盤内部を分けて計測する。
5. 実際のDedicated Workerで映像と音声を読み、H.264/AAC MP4をファイルへ確定し、同期と復帰を検証する。
6. `expectedFrames` を省略して映像・音声を途中で揃えて止め、finishで有効なMP4になることを確認する。
   映像0枚や許容範囲を超える音声長の不一致は従来どおり拒否する。cancelは破棄のまま。
7. 境界・空白・重複取得の回帰テストを通し、終了したフレームを選ばず、返却物の独立した所有権を保証する。
8. WebGLからCanvas／VideoFrameを経由したMP4出力を検証する。Worker経路と回転／flipの再現も含める。
9. 二動画＋音声の評価結果として処理時間・シーク初動・資源推移を記録し、検証環境と未検証環境を明記する。
10. 既存39件のテストを維持し、公開APIの互換性を確認する。

## 0.3：ブロック単位のサンプルレート変換

まず44.1 kHzと48 kHzの相互変換、モノラル／ステレオを対象にする。
PCMブロック列を受け、指定レートのPCMブロック列を返す独立モジュールを候補とする。

- 連続区間ごとに変換状態を保持する。ブロックごとに位相・フィルターを初期化しない。
- 累積サンプル数とレート比で時刻を管理し、ブロックごとの端数丸めを足し合わせない。
- 終端のflush、フィルター遅延、末尾の扱い、出力サンプル数の丸め方を仕様化する。
  一つの連続区間では、flush後の長さが規定の丸め規則による総サンプル数と一致することを完成条件にする。
- サンプルレート変更・シーク・別曲への切り替えは新しい区間として明示する。
  無音挿入、重なりの解消、フェードは行わない。アプリは変換後の実サンプル数を使って配置する。
- ダウンサンプリング時の折り返しノイズを抑える方式を採用する。
  基盤の線形補間をそのまま汎用の高品質変換として公開せず、成熟した変換器の採用も比較する。
  非公開内部モジュールへの直接importは避け、Worker対応、メモリ、依存サイズ、ライセンスを確認する。

音源ごとにレートを揃えてから同じwriterへ追加する。writer自体に異なるレートを無条件で投入する仕様にはしない。
一括入力と不規則なブロック分割の結果、インパルス、連続波形、スイープ、10曲相当の切り替えを比較する。
欠落・重複・時間ずれに加え、変換器が生む境界ノイズと周波数特性を検証する。
元音源同士の不連続で生じるクリック音はフェード等で処理するアプリの問題として区別する。

## 時刻メタデータと色の情報

パケット時刻APIは、0.2の読み取りキャンセル機構を再利用して小さく追加する候補とする。
PTS、duration、decode順序を示すsequenceNumber、key/delta等を逐次返し、圧縮本体は返さない。
デコードできないトラックでも、解析できるメタデータは取得できる設計にする。

初期の返却順は基盤と同じデコード順に固定して明記する。Bフレームのある動画ではPTSが単調とは限らない。
二本の配列を同じ行番号だけで比較しても表示の一致は保証できない。
アプリがPTSで対応付け、実際の表示フレームの検証にはvideoFramesも使う。
表示順へ全件ソートしてから返す方式は、逐次取得APIには持ち込まない。

トラックの時刻分解能を併せて公開する。圧縮パケット時刻とWebCodecs経由のµs精度を区別し、
不明・取得不能な値を推測で埋めない。基盤から得られない生のDTSや元の整数tickを正確値として創作しない。
パケット数とデコードフレーム数を同一視しない方針を維持する。
0.2ではvideoFramesのデコード後の表示時刻を比較して二動画の同期評価を進める。
パケット単位の検査はこのAPIの追加後とし、0.2の完了待ち条件にしない。

色については、probe／MediaFrameに基盤から得られる色域・伝達特性・行列・full/limited rangeを
公開する小さな追加を検討する。メタデータの申告値と、出力で実際に観測した値を区別し、不明は不明のままにする。
グレーマット専用補正、HDR変換、ブラウザーをまたぐ画素値の完全一致は次版の保証対象にしない。

## 検証を継続する方法

Playwrightで公開APIを使い、生成ファイルをFFmpeg／ffprobeで独立検査する現行方式を継続する。
新機能のテストは後回しにせず、その機能と同じ変更に含める。

| 検証 | 完成時に確認・記録するもの |
|---|---|
| 連続取得・反復シーク | 元フレームの番号、PTS、境界・空白、重複取得の所有権、return完了後の再利用と旧処理の解放 |
| 長尺の実ファイル出力 | 正常なfinalize、先頭・中間・末尾のA/V同期、ゆっくり書く保存先での処理待ち |
| メモリ | 保持PCM・ハンドル数・JSヒープ、取得可能ならプロセス指標。MP4索引の正常な増加とリークを区別 |
| Worker | Window APIへの偶発的依存、対応確認、AAC登録、保存、中止、再実行 |
| WebGL出力 | 二動画の描画、Canvas／VideoFrameの受け渡し、Worker、回転／flip、既知の目印と画素値 |
| レート変換 | ブロック分割に依存しない総サンプル数、境界、遅延、折り返しノイズ |
| 黒・白・グレーの往復 | デコード直後、Canvas 2D／WebGL描画後、再エンコード後の値と色メタデータ |
| 実用性能 | 二動画の連続取得時間、シーク後の初動、描画・書き出し時間。測定範囲と素材条件も記録 |

長尺は、通常テストに短い再現ケース、リリース前に30～60分の素材時間を持つ試験を分けて用意する。
尺が長い素材を一括PCM展開して試験自身がメモリを使い切らないよう、入力・正解データも逐次生成／検査する。
時間ずれは冒頭だけでなく末尾まで測る。性能値にはブラウザー、OS、解像度、コーデックを記録する。
色差とメモリの合否閾値は初回計測で根拠を残して設定し、未測定の数値を保証として先に掲げない。

### 0.2の性能レポートと利用環境

通常区間の負荷である「動画2本＋音声1本」を基準とし、少なくとも以下を記録する。

- 二動画の連続取得: 各入力のフレーム数、対象素材時間、実処理時間、二入力が同じ要求時刻に揃うまでの時間。
  読み取りだけの測定と、WebGL描画・音声・書き出しを含む測定を分ける。
- シーク初動: return完了後の新規読み取り開始から、最初の使用可能なフレームが返るまでの時間を各入力で測る。
  二入力が揃うまでの時間も示す。中止要求から測った再開全体の時間は別項目にする。
- 初回と反復時を分け、試行回数、中央値、p95、測定区間・ウォームアップ条件を記録する。
  キーフレーム位置に近い／遠いシーク、順方向／逆方向も区別する。
- ブラウザー名・バージョン、OS、CPU／GPU（取得可能な範囲）、実行場所（Window／Worker）、
  WebGL実装（ソフトウェア描画を含む）、解像度、fps、コーデック、Bフレーム・GOP等の素材条件を付ける。
  ハードウェアアクセラレーションの希望設定と、実際に確認できた情報を区別し、不明は不明とする。
- AACは実際に使用したnative／WASM経路を結果へ保存する。
  native対応判定、native経路での実測、WASM経路での実測を混同しない。
- メモリ・資源は開始時／途中／完了後に記録し、PCM、フレームハンドル、読み取りキャッシュ、
  旧処理、MP4索引、取得可能なプロセス指標を分ける。JSヒープだけでGPU／デコーダー全体の上限を主張しない。

利用先はWindowsのChrome／Edge。ライブラリ側がLinux Chromiumで検証した段階では、
Windows Chrome／Edgeは未検証と明記し、その結果をWindowsの動作保証へ読み替えない。
Windows確認は編集アプリへの組み込み時に同じ素材・測定手順で実施し、結果を別行として追加する。
Linuxでの0.2完成とWindowsでの利用確認を別の到達点として報告する。
実行不能・未実行・失敗・成功を区別し、AACやWebGLが利用できない環境を黙って成功扱いにしない。
全環境での30fps再生や一定のシーク応答時間を保証するものではない。

0.2の引き渡し物は、API契約、WebGL／Workerの最小サンプル、回帰テスト結果、長尺・性能レポート、
Windowsで再現するための素材と手順とする。測定結果は別紙の0.2評価結果に記録する。

## 実装の順序

1. 読み取りの寿命・所有権・終了処理を共通化し、return完了と再利用、旧処理が累積しないことを先に検証する。
2. videoFramesとvideoFramesAtを追加し、境界・空白・所有権を検査する。表示変換メタデータも補完する。
3. PCMブロック入力とwriter.addPcmを追加し、Workerでの映像＋音声の往復を検証する。
4. 二入力のWebGL出力例、長尺出力・早期finish、既存APIの回帰確認を完了する。
   処理時間・シーク初動・メモリ・環境を報告し、0.2を区切る。
5. その実利用結果を踏まえ、独立したレート変換を実装する。パケット時刻と色メタデータの小さな追加を組み合わせる。

0.2の完了を、0.3の変換器選定や編集アプリのUI完成待ちにはしない。
各段階で得たサンプルを編集アプリ側へ渡し、ライブラリに編集・合成ポリシーを持ち込まずに評価する。
